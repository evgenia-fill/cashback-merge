# CashBackMerge

Консольная игра с механикой, похожей на 2048.

На игровом поле находятся плитки со значением кэшбэка. Плитки с одинаковым значением могут объединяться, образуя плитку с удвоенным значением.

Например:

```text
1 + 1 -> 2
2 + 2 -> 4
4 + 4 -> 8
```

Правила кампании задаются через JSON-конфиг.

## Конфигурация

Пример `campaign.json`:

```json
{
  "boardSize": 4,
  "movesLimit": 100,

  "spawnRules": [
    { "cashback": "1", "probability": "0.85" },
    { "cashback": "2", "probability": "0.15" }
  ],

  "rewardTable": [
    { "cashback": "2",  "reward": "0" },
    { "cashback": "4",  "reward": "50" },
    { "cashback": "8",  "reward": "150" },
    { "cashback": "16", "reward": "500" },
    { "cashback": "32", "reward": "2000" }
  ],

  "maxRewardCashback": "32",
  "maxRewardAllowedRate": "0.20"
}
```

### Параметры

- `boardSize` — размер игрового поля. В базовой конфигурации используется поле `4 × 4`;
- `movesLimit` — максимальное количество ходов, изменивших состояние поля;
- `spawnRules` — правила появления новых плиток;
- `cashback` — значение плитки;
- `probability` — вероятность появления плитки с данным значением;
- `rewardTable` — таблица наград в зависимости от максимальной достигнутой плитки;
- `maxRewardCashback` — значение плитки, соответствующее максимальной награде;
- `maxRewardAllowedRate` — максимально допустимая доля игроков, получивших максимальную награду.

Значения кэшбэка и вероятностей хранятся строками, чтобы явно контролировать преобразование чисел и не терять точность при работе с конфигурацией.

## Валидация конфигурации

Валидация выполняется классом `ConfigValidation`.

Конфигурация считается валидной, если:

- `movesLimit > 0`;
- список `spawnRules` не пуст;
- `cashback` каждого правила является положительным целым числом;
- каждая вероятность положительна и не превышает `1`;
- сумма вероятностей всех правил равна `1`.

## MR1 — Модель и конфигурация

В MR1 реализованы:

- состояние игровой сессии;
- лимит ходов;
- загрузка конфигурации из JSON;
- валидация конфигурации;
- взвешенный выбор значения новой плитки;
- выбор случайной свободной клетки;
- воспроизводимая генерация начального состояния по `seed`;
- текстовый вывод поля.

### Игровая сессия

`GameSession` хранит состояние одной партии:

- игровое поле `Board`;
- размер поля `BoardSize`;
- лимит изменивших поле ходов `MovesLimit`;
- количество уже использованных ходов `UsedMoves`;
- текущий `Score`;
- статус партии `Status`.

Пустая клетка представлена значением `0`.

### Начальное состояние

При создании `GameEngine` создаётся новая игровая сессия и размещаются две начальные плитки.

Количество стартовых плиток — `2`. Это выбранное правило реализации, так как конкретное количество стартовых плиток в условии не задано.

Для генерации случайных значений используется фиксированный `seed`:

```csharp
new Random(seed)
```

Один экземпляр `TileSpawner` живёт в течение всей партии, поэтому последовательность случайных событий воспроизводима.

Одинаковые конфигурация и `seed` приводят к одинаковой последовательности появления плиток.

### Появление плиток

`TileSpawner` отвечает за появление новой плитки.

При спавне:

1. находится список свободных клеток;
2. случайно выбирается одна из них;
3. значение плитки выбирается согласно вероятностям из `spawnRules`;
4. выбранное значение записывается в выбранную клетку.

Например:

```text
1% -> 0.85
2% -> 0.15
```

означает, что плитка `1` появляется с вероятностью `85%`, а плитка `2` — с вероятностью `15%`.

## MR2 — Движок ходов

В MR2 реализован игровой движок, который поддерживает четыре направления:

```text
UP
DOWN
LEFT
RIGHT
```

Полный игровой ход выполняется методом:

```csharp
ApplyMove(MoveDirection direction)
```

`GameEngine` отвечает за применение правил игры, а `GameSession` хранит состояние текущей партии.

### Движение плиток

Алгоритм движения разделён на два уровня.

`MoveInDirection` отвечает за обработку всего поля, а `MoveLine` — за обработку одной строки или одного столбца.

Для движения влево строка обрабатывается непосредственно:

```text
[1, 1, 0, 0]
        ↓
[2, 0, 0, 0]
```

Для движения вправо строка разворачивается, обрабатывается тем же алгоритмом и разворачивается обратно.

Аналогично работают движения вверх и вниз, только вместо строк обрабатываются столбцы.

### Правила объединения

Перед объединением пустые клетки удаляются из обрабатываемой линии.

Например:

```text
[1, 0, 1, 1]
        ↓
[1, 1, 1]
        ↓
[2, 1]
        ↓
[2, 1, 0, 0]
```

Поддерживаются правила:

```text
[1, 1, _, _] -> [2, _, _, _]
[1, 1, 1, _] -> [2, 1, _, _]
[1, 1, 1, 1] -> [2, 2, _, _]
[2, 2, 4, 4] -> [4, 8, _, _]
```

Одна плитка может участвовать в объединении не более одного раза за ход.

Например:

```text
[1, 1, 2, _]
        ↓
[2, 2, _, _]
```

Получившиеся две плитки `2` не объединяются повторно в рамках того же хода.

### Ход без изменения поля

После расчёта нового состояния движок сравнивает его с текущим полем.

Если положение и значения всех плиток остались прежними, ход считается ходом без изменения поля.

Такой ход:

- возвращает `MoveResult` с `IsChanged = false`;
- не увеличивает `UsedMoves`;
- не изменяет `Score`;
- не создаёт новую плитку.

### Изменивший поле ход

Если поле изменилось:

1. новое состояние записывается в `GameSession`;
2. при наличии объединений увеличивается `Score`;
3. появляется ровно одна новая плитка;
4. `UsedMoves` увеличивается на `1`;
5. проверяется достижение лимита ходов.

После достижения:

```text
UsedMoves >= MovesLimit
```

статус партии становится:

```csharp
GameStatus.Finished
```

Ходы, не изменившие поле, в `MovesLimit` не учитываются.

### Score

В текущей реализации `Score` увеличивается только при объединении плиток.

При каждом объединении к счёту добавляется значение получившейся плитки.

Например:

```text
1 + 1 -> 2   score +2

2 + 2 -> 4   score +4

[2, 2, 4, 4] -> [4, 8, 0, 0]
score +4 +8 = +12
```

Простое перемещение плиток без объединения не увеличивает `Score`.

`rewardTable` не используется для расчёта `Score`: таблица наград относится к определению итоговой награды.

### Завершение партии

Получение плитки `32%` само по себе не завершает игру.

Партия продолжается до тех пор, пока не будет использован лимит изменивших поле ходов:

```text
UsedMoves == MovesLimit
```

После этого `GameSession.Status` становится `Finished`, а дальнейшие вызовы `ApplyMove` запрещены.

## Основные компоненты

`GameEngine` — управляет игровой логикой и применением ходов.

`GameSession` — хранит текущее состояние партии.

`TileSpawner` — выбирает значение и позицию новой плитки.

`ConfigValidator` — проверяет корректность конфигурации.

`JsonDeserializer` — загружает конфигурацию из JSON.

`ConsoleGame` — отвечает за текстовое отображение игрового поля.


## MR3 — Награды и симуляция

В MR3 реализованы:

- определение награды по максимальной плитке;
- стратегия `random`;
- batch-симуляция нескольких партий;
- воспроизводимость по `seed`;
- расчёт статистики;
- JSON-отчёт;
- проверка ограничения `actualMaxRewardRate <= maxRewardAllowedRate`.

### Награды

После завершения партии определяется максимальная плитка и по `rewardTable` выбирается награда.

Например:

```text
16 -> 500
32 -> 2000
```

Если максимальная плитка больше последнего tier из `rewardTable`, используется максимальная награда.

Например:

```text
64 -> 2000
```

### Симуляция

`GameSimulator` запускает указанное количество независимых партий.

Для каждой партии создаются новые:

```text
GameEngine
TileSpawner
RandomMoveStrategy
```

Для всей симуляции используется общий `seed`, из которого генерируются отдельные seed для партий.

Поэтому одинаковые:

```text
config
seed
strategy
players
```

дают одинаковый результат симуляции.

### Статистика

После симуляции рассчитываются:

- распределение максимальных плиток;
- распределение наград;
- средний `Score`;
- максимальный `Score`;
- `actualMaxRewardRate`.

`actualMaxRewardRate` — доля игроков, получивших максимальную награду:

```text
actualMaxRewardRate = playersWithMaxReward / playersCount
```

После этого проверяется:

```text
actualMaxRewardRate <= maxRewardAllowedRate
```

Если условие выполняется:

```text
OK
```

иначе:

```text
FAILED
```

### JSON-отчёт

Отчёт содержит:

- конфигурацию;
- `seed`;
- количество игроков;
- стратегию;
- распределение плиток;
- распределение наград;
- средний и максимальный `Score`;
- `actualMaxRewardRate`;
- статус `OK` или `FAILED`.

### Запуск

Из корня репозитория:

```bash
dotnet run --project ./src/CashBackMerge.App/CashBackMerge.App.csproj -- simulate \
  --config campaign.exemple.json \
  --players 10000 \
  --strategy random \
  --seed 67 \
  --output report.json
```

После выполнения создаётся файл `report.json`.

## Принятые правила реализации

- в начале партии создаются две плитки;
- достижение `32` не завершает игру;
- партия завершается при достижении лимита ходов или отсутствии доступных ходов;
- плитки выше максимального tier получают максимальную награду;
- `Score` увеличивается на значение плитки, созданной при merge;
- пустая клетка представлена значением `0`.

## Тесты

Проверяются:

- валидация конфигурации;
- воспроизводимость по `seed`;
- правила merge;
- запрет двойного объединения;
- ход без изменения;
- появление одной плитки после изменившего хода;
- weighted random;
- соответствие награды tier;
- распределения в отчёте;
- `actualMaxRewardRate`;
- статус `OK` / `FAILED`;
- одинаковый отчёт при одинаковых входных параметрах.


## Бонус: Greedy-стратегия

Помимо случайной стратегии `random`, реализована стратегия `greedy`.

`GreedyScoreStrategy` оценивает каждый доступный ход через `BoardMover` и выбирает направление, которое даёт максимальный прирост `Score` на текущем ходу.

Если несколько направлений дают одинаковый `Score`, выбирается первое из доступных.

Запуск:

```bash
dotnet run --project ./src/CashBackMerge.App/CashBackMerge.App.csproj -- simulate \
  --config campaign.exemple.json \
  --players 10000 \
  --strategy greedy \
  --seed 67 \
  --output greedy-report.json
```

### Сравнение стратегий

Обе стратегии запускались на одинаковых:

```text
config
seed = 67
players = 10000
```

Результаты:

| Метрика | random | greedy |
|---|---:|---:|
| Average Score | 407.7744 | 501.2732 |
| Max Score | 582 | 592 |
| Max reward rate | 0.9225 | 0.9977 |
| Status | FAILED | FAILED |

Распределение максимальных плиток для `random`:

```text
8  -> 35
16 -> 740
32 -> 4659
64 -> 4566
```

Распределение максимальных плиток для `greedy`:

```text
16 -> 23
32 -> 2279
64 -> 7698
```

`GreedyScoreStrategy` заметно увеличивает средний `Score`:

```text
407.7744 -> 501.2732
```

и значительно чаще приводит к плитке `64`:

```text
random -> 4566 игроков
greedy -> 7698 игроков
```

При этом доля игроков с максимальной наградой также растёт:

```text
random -> 0.9225
greedy -> 0.9977
```

То есть стратегия, оптимизирующая текущий `Score`, оказывается выгоднее для игрока, но ещё сильнее нарушает бизнес-ограничение кампании:

```text
maxRewardAllowedRate = 0.20
```

Поэтому обе стратегии получают статус `FAILED`
